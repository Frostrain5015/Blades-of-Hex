# Blades of Hex 战场渲染与水域系统升级计划

> 状态：完整重构计划 v1.2（2026-07-14；拆分视觉原型已通过验收，生产实现进入集成回归与性能复核）
> 范围：渲染基础设施、2.5D 视觉语言、战场交互提示、水域/河流与编辑器配套
> 本轮已进入生产实现。`campaign/terrain-texture-preview.html` 是轻量目录页，具体金样按下文拆页验收；`operation-arrow-preview.html` 继续作为零改动设计备份。

## 1. 结论先行

1. **继续保留六边格规则和原生 ESM 模块边界，引入 Vite 作为开发与生产构建工具，不引入 React/Vue 接管战场。** 战场是高频、逐帧、强图层关系的场景；Canvas/Pixi 渲染后端只管画面，现有 DOM 继续管大厅、编辑器、弹窗和表单。
2. **PixiJS 作为按收益扩张的 GPU 后端，不直接替换完整 Canvas 管线。** 当前生产默认仍是 Canvas2D，Pixi 通过只读快照接管高频交互垂直切片；只有后续同场景压力测试证明收益，才扩大到更多画面层。WebGPU 只作为可选实验通道，Canvas2D 至少保留到 Pixi 版本通过全部视觉、功能与性能验收。
3. **不是一次性“换引擎”。** 对局状态、战斗规则、寻路、外交、触发器、WebSocket 协议均不进入 Pixi；Pixi 只消费只读的渲染快照和插值事件。
4. **视觉方向采用“战史线描地貌 + 低矮浮雕 + 球状单位徽章”。** 地形身份必须分布在六边格边缘和跨格连续结构中，不能依赖会被生产尺寸单位遮住的中央区域。
5. **环状血条保留，但不画在球面上。** 它被定义为球状徽章的外缘仪表框：暗色外交关系底轨常驻，亮弧长度表示生命，护盾使用更外侧的青色短弧。行动发起态另使用限制在单格内的“斜纹圆形地标 + 外环”；它位于单位下方、跟随动作色，不是叠在 HUD 上的第三条生命/护盾同心环。
6. **可移动范围只画一个连通区域，不给每个可达格画箭头。** 悬停某个终点时，才根据现有 `moveParents` 重建一条行军箭头；攻击目标使用单位准星，悬停时才出现一条强袭或火力箭头。
7. **水域不属于任何阵营。** 实体海域占据六边格；河流是吸附于六边格顶点的线网。国界、区划和阵营底色都跳过水域，海岸线由陆海邻接关系自动生成。

- 共享脚本外置但单页仍同时渲染全部 Canvas，不算完成拆分。

## 2. 为什么现在值得升级

当前 Canvas2D 引擎已经支持动态阵营、无边地图、国界/区划线、战争迷雾、将领先锋旗、WebGL 旗面形变、任务高亮和大量技能特效，证明逻辑层并不需要推倒重来。真正的瓶颈是：

- 每帧重新绘制大量不变的地块、纹理和边界，CPU 成本会随地图与特效规模线性增长；
- 地形、单位、旗帜、光圈、边界和前景遮挡依赖手写调用顺序，继续加层会越来越难维护；
- 单个 emoji 无法承担森林、山脉、城镇、工事和水体的连续空间表达；
- 当前逐格范围光圈在可达格很多时噪声大，也很难和未来的 2.5D 地貌共存；
- Canvas2D 与现有 WebGL 旗帜合成已经形成双渲染路径，继续增加 GPU 效果时状态同步成本会提高。

PixiJS 的价值主要来自场景树、批处理、纹理图集、RenderTexture、遮罩、滤镜、事件系统和稳定的 WebGL 管线；不是为了给现有代码换一种 API 写法。

## 3. 技术路线

当前生产基线是“Canvas2D 完整后端 + 懒加载 PixiJS 交互增强层”：Vite、PixiJS、`BattlefieldSnapshot`、后端设置和固定图层容器已经进入仓库。渲染 DTO 仍只由本地状态派生，不是协议命令，也不会反向修改 `gameState`。Canvas 继续负责完整可玩画面和 WebGL 故障回退；Pixi 目前只消费高频交互描述符，尚未成为默认完整场景后端。

### 3.1 构建系统

采用 Vite，但第一阶段保持业务代码为原生 ESM JavaScript：

- 浏览器开发阶段仍按模块组织，获得依赖预构建、快速启动与 HMR；
- 允许 `import { Application } from 'pixi.js'` 这类裸包导入；
- 生产构建统一处理哈希、缓存、资源 URL、动态分包和 source map；
- 编辑器、标准对局、战役对局可拆成独立入口与异步 chunk；
- TypeScript 只从新增的渲染接口、场景快照和地图 schema 开始渐进引入，不进行全仓一次性迁移；所有新增 TypeScript 禁止 `any`。

React/Vue 不进入战场渲染循环。若未来 DOM UI 复杂度显著提高，可只在编辑器或大厅局部评估，但不能让框架状态成为对局状态的第二真相源。

### 3.2 渲染后端

已建立的迁移接口：

```ts
type RendererBackend = 'canvas2d' | 'pixi-webgl' | 'pixi-webgpu';

interface BattlefieldRenderer {
  initialize(host: HTMLElement, options: RendererInitOptions): Promise<void>;
  syncScene(snapshot: BattlefieldRenderSnapshot): void;
  enqueue(event: BattlefieldVisualEvent): void;
  resize(viewport: BattlefieldViewport): void;
  render(frame: RenderFrame): void;
  destroy(): void;
}
```

约束：

- `BattlefieldRenderSnapshot` 是只读 DTO，不暴露可修改的 `gameState`；
- 输入系统先把屏幕坐标转换为棋盘坐标，再交给规则层判定，不能把规则写进 Pixi 的 pointer handler；
- 动画只消费 `BattlefieldVisualEvent`，动画结束不能反向改变战斗结果；
- 后端选择由启动配置、能力检测和用户降级设置共同决定；
- WebGL 初始化、运行时 context lost 或资源加载失败时自动回退 Canvas2D，并记录遥测。

PixiJS 当前版本已经有实验性 Canvas renderer，但它在功能覆盖和稳定性完全达标前不作为唯一兜底。旧 Canvas2D 后端仍是兼容基线。

### 3.4 静态缓存与纹理资产

- 以 8×8 或 12×12 六边格为一个静态地图 chunk，地形或归属变化时只使相邻 chunk 失效；
- 战史线描地形以小型纹理图集和程序化组合为主，避免为每格生成独立大纹理；
- 本次原型中的 Canvas2D 程序纹理可在迁移时先绘制到 `OffscreenCanvas`，再通过 Pixi `CanvasSource` 上传为纹理；当前生产地形仍以阵营底色和 emoji 为主，不能把原型纹理误称为既有生产资产。上传只允许发生在初始化或脏区重建时，禁止每帧 Canvas→GPU 拷贝；
- 单位徽章、状态环和常用图标使用共享几何/纹理；旗帜 SVG 先按实际屏幕需求栅格化并纳入图集；
- 缩放时设置明确的 mipmap、resolution 与 scaleMode，防止此前旗帜低分辨率问题重现。

## 4. 视觉规范

### 4.1 地形

采用用户确认的战史线描风格：中性色墨线、低饱和填色、少量浮雕阴影。阵营色仍是地块第一信息，纹理只以透明叠加、乘色或中性描边出现。

地形身份必须满足：

- 单位徽章按当前绘制基准 `HEX_SIZE = 30`、球体半径 15px 遮住中央时仍可识别；当前 15px 只是 `drawUnit()` 内部的局部 `badgeR` 常量，迁移时必须先抽成共享只读视觉度量，不能假定单位对象已有 `badgeR` 字段；
- 森林靠边缘树冠密度和跨格林缘连接，不靠中央一棵树；
- 山地靠跨格山脊走向与坡脚，不靠中央山峰；
- 城市只在城市 footprint 外圈绘制连续城郭，内部用街巷、屋顶边缘和广场留白区分；
- 防御工事沿地块边缘或指定朝向铺设，不和单位徽章争中央；
- 高射阵地双炮管统一朝右上方伸出，并比当前纹理略长；生产尺寸球状单位与外缘仪表覆盖后，炮口和主要炮管方向仍须在单位右上侧清晰露出；
- “显示网格”成为正式设置；关闭网格只隐藏普通格线，不隐藏国界、海岸、河流、城市外墙和交互边界。

### 4.2 球状单位与生命值

最终采用“外缘仪表环”：

- 球体：阵营主旗色的径向渐变、上左高光、下右暗部、低矮投影；
- 单位图标：位于球面中央，不承担生命或外交颜色；
- 外缘暗轨：以当前观察者视角的外交色低亮度绘制完整一圈；
- 生命亮弧：同一外交色高亮，长度为 `displayHp / maxHp`；
- 护盾：更外侧青色短弧，长度为 `displayShield / maxHp`；
- 生命亮弧与护盾弧必须使用同一个 12 点方向起点并沿同一方向增长；两者数值彼此独立，但读数基准绝不能错位；
- 标准对局可继续按健康状态着色；战役模式保持自身绿、联盟蓝、中立黄、敌对红；
- 低血量不能让外交信息完全消失，因此未填充部分不是纯黑，而是低亮度关系色；
- 生命值插值、受击闪烁和治疗回填只改变亮弧，不改变球面尺寸。

#### 不可突破的尺寸预算

- 单位球体继续使用当前生产绘制值 `HEX_SIZE = 30`、球体半径 15px，不得因 2.5D 高光而放大几何尺寸；Phase 2 先把 `drawUnit()` 的局部 `badgeR` 抽成渲染器共享视觉度量，供箭头锚点、命中框和 HUD 使用，但不写入规则单位或网络快照；
- 当前生产版护盾最外缘约为 `ringR 19 + lineWidth 2.4 / 2 = 20.2px`，新版球体、生命表圈、护盾弧及其实体描边必须全部落在该半径内；
- 发光可使用低透明度软边，但不能形成遮住旗面下缘的实色视觉面积；发生冲突时整体表圈略微向内缩，绝不移动或放大旗帜来迁就状态环；
- `UNIT_FLAG_LAYOUT`、城市/村庄旗位、旗面宽高和精调偏移保持现值，不属于本次视觉重构的可调整项；
- 旗杆仍在单位前绘制，球状徽章随后绘制，旗面布料在单位之后合成，确保状态环不能压住旗面；
- 增加单位+生命+护盾的屏幕包围盒截图回归：无盾、满盾、100%/32%/1% 生命、将领旗和普通旗均需覆盖。

移动、近战攻击和远程攻击的发起单位统一使用单格圆形地面标记：内圆采用动作同色的低透明填充与斜纹，外侧增加一圈低频呼吸环，整体不得越过所在六边格。标记进入 `interactionRoute` 并先于单位绘制，由球状单位自然遮住中央；它表达“动作从这里发起”，不是 `unitHud` 中的生命/护盾第三环。士气、军衔、将领绶带保持各自既有位置，避免把状态继续堆到单位外缘。

### 4.3 操作提示

#### 移动

选中可行动单位后：

1. 把 `movableTiles` 转成集合；
2. 复用区域边界算法，只绘制一圈连续的青绿色外边界；
3. 区域内部统一铺一层约 0.12–0.14 alpha 的青色半透明高亮，选中单位时复用旧方案按六边格距离由近到远展开的轻微果冻涟漪节奏；展开只作用于填色的透明度与尺寸，完成后形成连贯区域，内部相邻格不描边；
4. 不为每个可达格绘制箭头；
5. 悬停某个可达终点时，沿 `moveParents` 反向重建唯一最短/最低耗路径；
6. 路径上只绘制一条按本节“操作箭头语法”定义的“行军箭头”；行动力消耗进入固定选择 HUD，不在终点下方生成浮动文字框；
7. 路径经过的格可轻微提亮，离开悬停立即清除。

#### 攻击

- 所有 `attackableTiles` 只给实际敌方目标绘制小型红色角标准星，不整格刷红；
- 悬停近战目标时绘制短而宽、末端收束的强袭箭头；
- 悬停远程目标时不读取 `moveParents`：只使用攻击者与目标坐标生成抽象预览轨迹，不复用或触发实际攻击弹体；
- 克制/被克、预计伤害和反击信息进入固定选择 HUD/侧栏，不在单位或目标格下方生成浮动文字框；
- 攻击箭头永远只显示当前悬停目标的一条，避免多目标时满屏箭头。

#### 操作箭头语法（以 `terrain-preview-actions.html` 为验收原型）

`operation-arrow-preview.html` 只作为独立设计备份保留，不在本轮改造中修改；动作箭头在 `terrain-preview-actions.html` 验收，与通用/空军选点分别在自己的页面验收。战场箭头不是普通折线加三角形。它必须通过**轮廓、端型、节奏和载荷**四个维度让玩家在不读文字的前提下分辨意图；每帧最多存在一条“当前操作”箭头。玩家侧只提供移动、近战攻击、远程攻击三种预览，其中**路线箭头子系统**只消费普通单位操作的 `move` 与 `attack`；WebSocket 协议仍有 `tacticalCard`、`activateSkill`、`endTurn` 等其他动作，它们不进入路线箭头系统。近战/远程不是新的网络动作，也不能只按攻击距离猜测：视觉层应从当前实际攻击分支使用的单位类型与无人机标记派生预览类别，并与远端回放已有的 `effects.attackerType` / `effects.attackerIsDrone` 语义保持一致。

| 语义 | 战场入口 | 主体与端型 | 动态载荷与终点反馈 |
|---|---|---|---|
| `march` 移动 | 悬停可达终点 | 复刻 `operation` 金样：约 13px 的同色相低透明路线底轨凝聚整体，其上叠加约 3.6px 的高亮动态虚线主轨；底轨不得发黑、描边或抢过主轨。使用实心三角端头，整条路线保持圆角 | 3 个同色低频前进行军折标；终点增加同色低频落位脉冲。行动力信息进入固定 HUD |
| `assault` 近战攻击 | 悬停近战目标 | 半透明进攻带从起点较宽、向目标逐步收窄；箭身在终点前形成细颈，随后连接一个尺寸明显大于箭身、轮廓独立的实心箭头 | 3 个前进折标；目标外侧一次性扩散冲击环，与红色角准星同源但不覆盖单位 |
| `fire` 远程攻击 | 悬停远程目标 | 无视 BFS 路径，只按攻击单位球体中心与目标单位球体中心生成轻微弯曲的单一红色亮轨；删除亮轨下方的暗色路径，不再使用会割裂箭身与载体的双层线；使用开口 V 形端头，不能伪装成部队移动或实际攻击弹道 | 一个抽象发光载体沿轨迹循环前进；载体接触目标球体外缘的同一时刻才启动向外扩散的脉冲环。载体不区分炮弹/子弹，不播放枪口焰、爆炸或伤害反馈 |

实现约束：

- **路径几何与单位锚点：**移动预览直接沿 `gameState.moveParents: Map<Tile, { remaining, fromZoC, parent }>` 从悬停终点回溯到 `selectedUnit.tile`，得到 BFS 六边格中心序列；渲染层再用受限 Catmull–Rom/Bezier 曲线平滑并按累计弧长采样，不能改变节点顺序或跨越未经过的格。所有路线的起点都使用选中单位球体的视觉中心，而不是从地块边缘或 HUD 外侧截断；路线先绘制、单位球体后绘制，让球体自然遮住内部线段，形成路线从单位内部连续伸出的效果。近战与远程攻击的几何终点同样是目标单位球体中心，箭身延伸到球体下方，箭头尖端和远程载体则停在共享球体半径度量的外缘并与球体接触，禁止留下人为安全间隙。移动没有受击单位，终点仍使用目标落位中心，并用同色脉冲光圈建立视觉锚点。攻击接口没有父节点路径：近战使用源与目标之间的短曲线；远程只取攻击与目标单位两个端点，禁止插入 BFS 节点。
- **预览与攻击演出边界：**`fire` 仅表示“当前单位可以攻击该目标”的预览语义，不读取实际弹种，不调用或复刻实际攻击中的发射器、弹体、枪口焰、爆炸、音效、伤害事件与时间参数。确认攻击后仍由现有战斗流程独立播放真实视觉特效；预览层只维护自身可循环、可随时取消且无状态副作用的抽象发光载体。
- **路线层级：**行军允许且必须保留一条与主轨共用相同平滑几何的同色相底轨；它只承担路线凝聚，不能被读成黑色外轮廓或另一条偏移路径。远程攻击仍严格只绘制一条高对比亮轨，禁止在其下方铺暗色路径或外围轮廓。描边使用圆角 `lineCap`/`lineJoin`。近战是自身完整的渐缩实心进攻带，不受行军/远程轨道约束。所有软辉光只能贴近对应主线，不能扩大实际点击或遮挡面积。
- **军图比例：**以 `HEX_SIZE = 30` 为基准，行军底轨约 `0.43 × HEX_SIZE = 13px`、同色相且透明度约 `0.10–0.14`；高亮虚线主轨约 `0.12 × HEX_SIZE = 3.6px`、透明度约 `0.9`，虚线节奏约 `18px/11px`。远程单一亮轨在 100% 缩放下约 3–4px，其软辉光不得呈现独立路径。强袭箭身半宽从约 `0.34 × HEX_SIZE` 收束到 `0.12 × HEX_SIZE`，只绘制到路径弧长的约 84%；独立箭头长度约 `0.92 × HEX_SIZE`，箭翼总宽必须显著大于箭身末端，并保持完整实心轮廓。
- **方向节奏：**虚线偏移、折标和远程抽象载体只向终点运动；它们是方向冗余提示，箭头头部仍是唯一主方向标记。动态元素随平滑曲线的累计弧长均匀分布，不按六边格数量硬编码，经过 BFS 拐点时不得堆叠、折跳或突然变向。
- **颜色与状态：**移动使用青绿，近战与远程攻击使用敌对红；颜色只表示阵营关系，**线型才表示动作类别**。当前后端没有独立“撤退”动作，任何后撤都继续走 `moveUnit(unit, targetTile)`、`actionType: 'move'` 与移动箭头，不增加 `retreat` 分支。无效目标只渲染短灰红阻断段和禁用标签，绝不借用完整攻击箭头。
- **起点选中：**`gameState.selectedUnit.tile` 不再使用固定黄色高亮框或虚线菱形。三种动作统一绘制限制在单格内的斜纹圆形地标与外环，颜色随动作变化：移动为青绿，近战/远程为敌对红。地标进入 `interactionRoute`，随后由单位和 HUD 覆盖中央；外环是地面交互语义，不进入生命/护盾 HUD，也不得遮住对应读数。
- **终点信息：**行动力、预计伤害、反击、克制与恢复量统一进入固定选择 HUD/侧栏；目标下方不生成文字框。远程预览的循环脉冲只表示目标锚点，不等同于真实命中伤害；实际命中反馈仅在确认攻击并进入战斗事件后播放。
- **图层与遮罩：**箭身、行军底轨、折标和轨迹进入 `interactionRoute`（单位之下），并延伸到起止单位球体中心；单位球体随后遮住内部部分，箭头尖端停在球体外缘。准星与远程载体到达后触发的脉冲环进入 `interactionTop`，保证脉冲从球体外沿立即可见。二者均受可见性与战争迷雾裁切，不能泄漏不可见单位、隐藏路线或目标属性。
- **缩放、触控与无障碍：**100% 缩放下保持上述行军 13px 低透明底轨、3.6px 高亮主轨和远程 3–4px 单亮轨比例；缩小后先减少折标/粒子，再保留端型、行军双层层级和远程单轨，放大后不无限加粗。`prefers-reduced-motion`、暂停和低性能档冻结虚线偏移、折标和粒子，但保留完整静态轮廓；触控继续沿用当前单击合法目标立即执行的输入流程，按压/命中反馈可短暂显示同一静态预览，但不增加二次确认或网络阶段。

生产实现已采用以下后端无关渲染 DTO，避免把原型 Canvas 绘制细节泄漏到规则层。它不是现有协议命令：当前联机入口发送的是 `actionType + state 快照 + effects + baseRevision`，服务端验证后接纳并转发快照；箭头 DTO 只在本地从现有状态派生，不加入协议。

```ts
type OperationAction = 'move' | 'attack';
type OperationArrowStyle = 'march' | 'assault' | 'fire';

interface OperationArrowVisual {
  action: OperationAction;      // 仅路线箭头；对应 moveUnit/attackUnit 的 actionType
  style: OperationArrowStyle;   // attack 由共享攻击视觉分类派生，不新增 melee/ranged actionType
  tilePath?: AxialCoord[];      // 仅 move：由 moveParents 回溯；渲染层不得改写通行结果
  sourceUnitId: string;
  targetTile: AxialCoord;
  colorToken: 'move' | 'enemy';
  preview: boolean;
}
```

共享攻击视觉分类必须覆盖当前生产分支：`archer` 归为炮击式远程，`_isDrone` / `drone` / `mgNest` 归为枪弹式远程，普通步兵与骑兵归为近战；路线预览最终仍统一使用抽象载体，不调用这些真实弹体。该分类函数同时供本地预览与远端 `effects.attackerType` / `effects.attackerIsDrone` 回放选择使用，避免两套 `switch` 漂移。

#### 对策卡与主动技能目标选择语法（以 `terrain-preview-targeting.html` 为验收原型）

当前实现已经提供统一入口，但还没有统一语义：普通对策卡点击后会把 `{ cardId, targeting, handIndex, commanderId? }` 写入本地 `gameState.cardTargeting`；天眼部署、无人机自爆和工程师碉堡分别以 `drone_deploy`、`drone_suicide`、`engineer_bunker` 伪卡牌进入同一状态。该状态属于 `ClientUiState`，远端状态同步时会被清空，协议中也不存在 `select`、`hover` 或 `confirm` 动作；只有合法目标被点击并实际执行后，才沿用现有 `tacticalCard`、`activateSkill`、`droneDeploy`、`droneSuicide`、`engineerBunkerStart` 等动作类型。因此新版目标预览必须保持纯本地、可取消、无规则副作用，不增加联机消息。

现有 `renderer.js` 只按 `targeting` 字符串给所有合法格绘制脉冲六边形，并把 `friendlyAny` 直接归类为绿色治疗。这会让强行军、部署将领和空运都被画成治疗加号；同时候选规则分别复制在 `renderer.js`、`input.js` 和 `gameLogic.js`，已经出现“高亮但不能点击”的偏差，例如 `emptyTile` 预览没有排除占用格、部署将领预览没有排除已配属将领的单位。升级时不能只替换绘制函数，必须先统一候选集合。

五类单位目标——敌对攻击、治疗、机动增益、将领挂载和护盾——共用同一视觉骨架：球体外侧方形四角框、不会降至不可见的低频呼吸，以及位于角框中央的半透明全息语义图案。合法候选状态已经完整显示这三层；当前 `hoveredTile` 不再增加另一套符号，而是统一放大角框、增强辉光与中央图案。目标球体下方不追加文字框；如需预计伤害、恢复量或效果数值，应进入固定选择 HUD/侧栏，避免随目标漂浮并遮挡战场。地块部署和区域中心仍使用地块插槽/范围边界，不强行套用单位球体框。

| 选择意图 | 当前代码入口 | 候选视觉 | 当前悬停视觉 |
|---|---|---|---|
| `hostile` 敌对单位 | `attackableTiles`、`enemyGlobal`、`drone_suicide` | 红色方形四角框 + 中央留空的四臂全息准星十字；所有合法候选持续清晰可见，但不整格刷红 | 角框放大，方框与准星辉光同步增强；不叠加扫描线或目标下方文字框。范围攻击另显示受影响区域边界，但不播放命中特效 |
| `heal` 治疗单位 | `heal: anyUnit` | 绿色方形四角框 + 中央绿色粗实心全息十字；必须按当前规则允许敌我任意单位，若要改为仅友军应另改规则契约 | 角框放大、绿色十字和辉光同步增强；预计恢复量如需显示则进入固定 HUD |
| `mobility` 机动增益 | `forceMarch: friendlyAny` | 青绿色方形四角框 + 中央垂直叠放、统一朝上的两个全息折形符号，不使用医疗加号 | 角框放大、双折标和辉光同步增强；`+MP`、再次行动信息如需显示则进入固定 HUD |
| `attach` 将领挂载 | `commanderDeploy: friendlyAny`，并排除已有将领单位 | 任务金方形四角框 + 中央军衔菱形和挂载竖线；已挂载单位不进入候选集合 | 角框放大、军衔图案和辉光同步增强；所选将领信息留在固定卡牌/HUD 区域 |
| `shield` 护盾 | `shieldTarget` | 冷蓝方形四角框 + 中央全息盾形符号 | 角框放大、盾形和辉光同步增强；只能预演，不能提前修改 `_shield` |
| `deploy` 地块部署 | `emptyTile`、`emptyFriendly*`、`drone_deploy`、`engineer_bunker` | 青蓝地块插槽：清晰静态六边轮廓 + 四角落点框，不复用单位准星 | 半透明单位/工事占位轮廓；根据真实限制显示邻接、领土、城市、山地、占用与视野结果 |

##### 空军对策卡的完整目标契约与独立原型模式

空军卡不能只套一个“红色攻击目标”或“蓝色空地”示例。`terrain-preview-air.html` 必须提供五张卡的独立切换，其中空运再拆为选单位、选落点两个连续阶段，形成至少六个可单独验收的画面状态。所有模式继续遵守上文统一语法：单位目标使用方形角框、呼吸和中央全息图案，悬停只做辉光、角框放大和图案增强，目标下方不出现文字框；地块目标使用落点插槽，范围伤害使用独立区域边界。空军专属的航程、防空、视野和天气是叠加约束层，不能替代候选端型。

| 卡牌/阶段 | 当前真实候选契约 | 原型必须组合的视觉层 |
|---|---|---|
| `airstrike` 空袭 | `enemyGlobal`：中心必须是敌方单位；遭遇战战争迷雾开启时仅可选当前**可见**目标。它是普通对策卡，不受上校 6 格航程限制 | 复用红色区域中心语法：所有合法敌军显示区域中心角标，悬停时展开中心及相邻 6 格完整受影响边界；叠加逐格防空风险层，但防空格仍是合法中心，不使用单体攻击准星 |
| `airdrop` 空降 | `emptyTile`：任何未占用地块；遭遇战战争迷雾开启时仅限当前可见格。当前规则没有上校航程、阵营、城市、山地等额外限制，不能擅自复用 `emptyFriendly*` 过滤 | 所有合法空地显示青蓝落点角框与统一伞兵全息徽章；防空覆盖显示为落地生命风险而不是禁用遮罩。敌方城市等当前可执行落点也必须保持可见，若以后增加地形限制应先修改规则契约 |
| `diveStrafe` 扫射 | `enemyGlobal`：敌方单位，且目标地块距己方存活上校不超过 6 格；遭遇战中还必须当前可见 | 红色全息准星角框 + 上校所在格的飞机全息发起标记 + 蓝色 6 格航程边界 + 红色防空覆盖；这是单体攻击，不显示周围 6 格范围 |
| `carpetBomb` 轰炸 | `enemyGlobal`：中心必须是敌方单位，且在上校 6 格内、遭遇战中当前可见 | 复用空袭的红色区域中心语法，并叠加上校所在格的飞机全息发起标记、6 格航程边界和防空覆盖；悬停展开中心及相邻 6 格。当前执行会对范围内所有有单位地块逐一结算、没有阵营过滤，因此友军也必须以“受影响”而非“可点击”端型显示 |
| `airlift` 空运第一段 | `friendlyAny`：己方单位且在上校 6 格内；按卡面和现有预览意图排除上校自身，按执行规则排除 `_imprisoned` 单位 | 上校所在格显示飞机全息发起标记；候选单位使用与空降相同的伞兵全息徽章，但承载在单位方形角框内。上校自身和禁锢单位不显示为合法候选。选中运输单位后保留加强的伞兵来源框，切入第二段时不复用增益双折标或治疗图案 |
| `airlift_dest` 空运第二段 | 本地伪卡牌 `emptyTile`：未占用、距上校不超过 6 格；遭遇战中要求当前**可见**，不是仅“已探索”。当前实现未限制阵营、城市或地形，落在敌方空城可触发占领 | 上校飞机发起标记与来源单位伞兵锁定框同时保留；所有合法落点使用与空降一致的伞兵徽章与地块角框，叠加上校 6 格边界和防空风险。悬停只放大落点徽章；来源—落点关系使用一条无暗色底轨的单一亮线 |

约束层必须按当前代码语义解释：

- **上校航程：**`COLONEL_CARD_DATA.range = 6` 只约束 `diveStrafe`、`carpetBomb`、`airlift` 两阶段，距离原点始终是存活上校所在格，不是被空运单位的起点；`airstrike` 与 `airdrop` 不显示这条航程边界，也不接受该硬限制。上校未部署、已阵亡或不存在时，三张上校专属卡应在进入选点态之前整体不可用，不能因为 `isColonelTargetBlocked()` 在“找不到上校”时返回 `false` 而错误放开全图候选。
- **飞机发起标记：**三张上校专属卡在上校所在格复用动作发起态的“单格斜纹圆形地标 + 外环”，中央叠加飞机轮廓全息图案；它只标识 `colonelOriginUnitId`，不替代上校单位、航程边界、防空来源或候选端型。普通 `airstrike`、`airdrop` 的当前后端没有棋盘发起单位，因此不得伪造 `originUnitId`、航程或协议坐标；原型若展示装饰性飞机只能放在固定说明区，不能锚定成规则地块。
- **防空不是阻挡：**敌方 `archer`、`mgNest` 以及挂载 `staller` 的单位在 `COLONEL_CARD_DATA.antiairRadius = 2` 内提供防空，`tile.fortification === 'flak'` 的高射阵地提供本格防空；最多 2 层。所有覆盖格统一使用斜纹而非纯色遮罩：1 层为单方向红色斜纹，2 层在同一格叠加反方向斜纹形成交叉纹，主要依靠纹理密度而不是仅靠深浅区分；防空来源单位/工事必须单独标出，减少动态效果时仍保留完整斜纹。攻击类 `airstrike`、`diveStrafe`、`carpetBomb` 每层提供 25% 的空军伤害减免，空降/空运则由 `applyAADropHP()` 每层从当前生命扣除相当于最大生命 25% 的数值并保底 1 HP。空运还先承受自身的 20% 当前生命损失（上限为最大生命 40%），这不是防空效果。预览绝不能把红色防空区从合法集合中删除。
- **先统一防空规则，再升级画面：**当前普通空袭的 `getAALayers()/applyAADefense()`、`Unit._resolveDamage(...isAirDamage)` 和 `renderer.js` 自建的布尔 `aaSet` 对高射阵地、驻军与层数的口径并不一致，渲染集合还无法表达 1/2 层。`flak` 也没有独立 `owner`/`fortificationCamp` 字段：现有 `getAALayers()` 无条件把目标格的 `flak` 计作一层，而旧预览仅在格内存在敌方驻军时显示。Phase 2 先把“空工事、驻军工事、敌我来源、工事机制开关”的权威语义冻结为测试，再抽取一个无绘制副作用的共享防空解析器，返回真实 `0 | 1 | 2`；普通空袭、上校扫射/轰炸、空降/空运结算、候选风险层和最终执行复核共同消费它，删除旧布尔 `aaSet`，迷雾层再过滤可展示的来源。原型的单斜纹/交叉斜纹是目标语法，不能反向证明当前三条代码路径已经统一，也不得为解决归属问题杜撰工事字段。
- **逐格风险：**空袭、轰炸的防空减伤按每个受影响单位所在格分别计算，不得只读取中心格并把同一结果复制给周围 6 格；空降和空运只读取最终落点。范围轮廓表示可能受影响集合，红色区域中心角标或伞兵落点徽章才表示可点击集合；扫射仍使用单体攻击准星。
- **战争迷雾与雾天：**`skirmishFog + isTileVisible()` 是候选过滤，不可见单位与地块不能因航程线、防空区、范围边界或全息框而泄漏；天气 `weather === 'fog'` 且开启 `weatherEffects` 时则是五张空军卡全部停飞，应在卡牌可用性层阻止进入选点并在原型提供统一的停飞状态。两者名称相近但不是同一规则。
- **空运一致性缺口：**现有 `renderer.js` 已排除上校自身与禁锢单位，但第一段执行校验只明确拒绝禁锢；第二段的占用、可见与 6 格限制又分散在输入和 `_executeAirliftDest()`，且后者通过 `airlift_dest` 提前分支绕过普通卡牌验证。统一候选解析器上线时，必须把“排除上校自身/禁锢、空格、当前可见、距上校 6 格”同时放入共享候选结果与最终执行复核，消除可见、可点、可执行三者漂移。

原型验收时，五张卡按钮不能只改标题或颜色：空袭与轰炸必须能比较“无航程/有航程”的差别，扫射与轰炸必须能比较“单体/范围”的差别，空降与空运落点必须能比较“全图可见空地/上校 6 格空地”的差别，空运两个阶段必须可连续预览。每个模式都要同时放入至少一个合法安全目标、合法防空风险目标和因航程/视野/占用/禁锢而非法的样本，以证明覆盖层没有篡改候选集合。

交互状态只有三层，不引入不存在的二次确认动作：

1. 进入 `cardTargeting` 后，所有合法单位候选立即显示高对比方形角框、低频呼吸与中央全息图案，确保无需逐格悬停即可扫读全图合法目标；非法目标保持原战场外观；
2. 桌面端用现有 `gameState.hoveredTile` 只强化一个当前目标：统一放大角框、增强辉光与全息图案，并按需显示范围边界；不在目标下方生成文字框，数值信息进入固定 HUD。触控端在卡牌或技能已进入选点态后仍按当前规则单击合法目标执行；
3. 点击后立即离开选点态并播放真实卡牌/技能效果；预览帧不得调用 `execute`、修改单位/地块状态或广播动作。再次点击卡牌、空白处、右键和 `Escape` 继续沿用现有取消路径。

候选规则现已抽为纯函数结果，同时供渲染、光标与点击确认使用，执行层仍保留最终校验。以下 `TargetShape`、`TargetIntent`、`AirTargetingOverlay` 与 `TargetingPreviewDescriptor` 是本地派生 DTO，不是协议字段；其中 `gameState.cardTargeting` 仍只保存选择流程状态，由解析器派生完整描述符：

```ts
type TargetShape = 'unit' | 'tile' | 'area' | 'option';
type TargetIntent = 'hostile' | 'heal' | 'mobility' | 'attach' | 'shield' | 'deploy' | 'transport' | 'reveal';

interface AirTargetingOverlay {
  phase: 'target' | 'airlift-source' | 'airlift-destination';
  colonelOriginUnitId?: string;     // 仅上校专属卡；普通空袭/空降不得设置
  rangeTileKeys?: Set<string>;      // 上校 6 格硬限制的可视边界
  aaLayersByTileKey: Map<string, 0 | 1 | 2>; // 风险信息，不参与候选剔除
  flightDisabledReason?: 'fog-weather' | 'colonel-unavailable';
}

interface TargetingPreviewDescriptor {
  source: 'combat' | 'card' | 'skill';
  actionId: string;                 // cardId、skillId 或 attack
  rawTargeting?: string;            // 兼容当前 targeting 字符串
  shape: TargetShape;
  intent: TargetIntent;
  originUnitId?: string;
  candidateTileKeys: Set<string>;   // 唯一候选真源；渲染/光标/点击共用
  hoveredTileKey?: string;
  affectedTileKeys?: Set<string>;   // 范围预演，不代表可点击集合
  air?: AirTargetingOverlay;         // 仅空军卡；供航程/防空/停飞叠加层消费
  executesOnClick: true;            // 对齐当前输入流程，不新增网络确认
}
```

##### 棋盘边界与无边假地块契约

当前可玩格的真实来源是 `gameState.tiles/tileMap`；无边地图边缘半格是带 `isVisualFiller: true` 与 `sourceTile` 的渲染对象，不进入 `tileMap`、不可命中。渲染层必须基于这两个现有来源**新增派生投影**，显式区分两套集合，不能再把“画出来的格”默认当成可玩格；当前代码不存在 `playableTileKeys`、`renderTileKeys` 或通用 `boardMask` 字段：

```ts
interface BattlefieldTileProjection {
  playableTileKeys: ReadonlySet<string>; // 可点击、寻路、序列化和发送协议坐标
  renderTileKeys: ReadonlySet<string>;   // 经典地图与 playable 相同；无边模式可加 render-only 假地块
}
```

- `candidateTileKeys`、`affectedTileKeys` 的规则结果、点击命中、BFS 节点和协议坐标只能来自 `playableTileKeys`；无边假地块永远不可点击、不可成为候选或真实受影响结果；
- 航程、防空、移动区域、范围填充等视觉投影先与 `renderTileKeys` 相交，集合外的键在创建 DisplayObject/几何之前直接跳过，不能生成后再依赖视口裁剪；
- 无边模式的假地块只允许承接阵营底色、地貌和连续纹理；若需要把某种区域纹理视觉延续到假格，只能由 renderer 从真实规则集合派生临时投影，不得把假格写回规则 DTO；
- 提取区域轮廓时，若相邻键不在 `renderTileKeys`，该边直接跳过，不能把棋盘裁切边误画成航程圈、防空圈或范围边界；只有相邻键仍在 `renderTileKeys`、但不属于当前语义区域时，才绘制真正的效果边界；
- 大面积填充、斜纹、辉光与滤镜统一受缓存的棋盘渲染蒙版约束，阻止几何已经越界跳过但 blur/filter 仍溢出地图外；
- `AirTargetingOverlay.rangeTileKeys` 与 `aaLayersByTileKey` 保持真实规则集合语义。无边假格上的连续纹理若存在，只是渲染投影，不得反向进入这两个字段。

首批一致性修正必须覆盖：`commanderDeploy` 排除已配属将领单位；`emptyTile` 排除占用格；天眼部署与工程师碉堡使用各自真实邻接和地形限制；空军卡按上文完整矩阵统一候选、航程、防空、视野、天气与空运两阶段终检。自身即时技能（狂战士、圣骑士、牧师、工程师战壕/高射机枪）不进入棋盘选点；占星者天气四选一继续使用选项弹层，也不伪装成地块目标。

#### 其他语义

- 任务目标：继续使用 EasyTech 式金色常驻脉冲；
- 普通剧情行军和后撤继续复用移动箭头，不新增独立动作样式；
- 卡牌范围：保留独立配色和边界样式，不能冒充普通移动范围；
- 无效目标：只在悬停时给出灰红色阻断反馈，不常驻污染战场。

## 5. 水域与河流

### 5.1 数据模型

水域采用“地块表面 + 顶点线网”两层模型：

```ts
type SurfaceKind = 'land' | 'shallowWater' | 'deepWater';

interface SurfaceSpec {
  q: number;
  r: number;
  kind: SurfaceKind;
}

interface RiverVertexRef {
  q: number;
  r: number;
  vertex: 0 | 1 | 2 | 3 | 4 | 5;
}

interface RiverPathSpec {
  id: string;
  width: 'stream' | 'river';
  points: RiverVertexRef[];
  navigable?: boolean;
}

interface RiverCrossingSpec {
  riverId: string;
  segmentIndex: number;
  kind: 'ford' | 'bridge';
}
```

导入时把物理上重合的顶点规范化为唯一 canonical key，防止相邻格重复顶点产生缝隙。每段河流只允许连接相邻顶点；编辑器自动吸附并拒绝零长度、跳点和自相交异常。

### 5.2 表现与规则

- `shallowWater`、`deepWater` 的 `camp` 必须为 `null`，不绘制阵营底色、国界和区划；
- 海岸由水陆相邻边自动生成，使用双层线描：深色岸线 + 淡色浪花；
- 相邻水格共享同一连续波纹方向，不做每格独立“蓝色贴纸”；
- 河流线位于地形上、单位下；桥梁和浅滩位于河流上并提供明确跨越点；
- 河流默认增加陆军跨越成本或阻止部分单位跨越，桥/浅滩覆盖该规则；
- 实体海域只允许 `naval`、`amphibious` 或处于运输状态的单位进入；
- 第一版海军只实现舰船单位、海域移动、基础近/远程攻击、港口上/下船，不引入复杂风向、补给线和舰队编制；
- 两栖切换必须在海岸/港口发生，陆军不能因路径算法直接“走进海里”。

### 5.3 编辑器

地图页签增加：

- 表面画笔：陆地、浅水、深水；
- 海岸预览：只读自动生成，可显示异常孤立水格；
- 河流笔：吸附六边格顶点，单击续点、双击结束、Backspace 撤回上一段；
- 桥/浅滩工具：只能放到已有河段；
- 港口工具：只能放在同时邻接陆地和实体水域的地块；
- 舰船单位类别与海军阵营预览；
- 校验器：无归属水域、断裂河流、非法桥梁、陆军出生在深水、舰船出生在陆地均为阻断导出错误。

## 6. 标准对局与战役兼容

- `boardLayout: 'hex' | 'borderless'` 继续决定地图外形，不决定渲染后端；
- 标准对局默认仍使用旧式六边地图与现有规则；新地形纹理可作为画面设置逐步开放；
- 战役作者可选择 `hex` 或 `borderless`，两者共享地形、单位、河流、水域和交互渲染；
- 未声明 `surface` 的旧地图全部迁移为 `land`；未声明河流/水域时行为与当前版本完全一致；
- 未声明新版视觉配置时，加载器补默认值，旧 JSON 无需人工重写；
- 战役指定旗帜、剧情将领、动态阵营和自定义回合顺序均只进入场景快照，不在渲染器内硬编码阵营数量；
- 标准对局自定义旗帜继续只在标准模式生效，战役剧情旗帜优先级不变。
- 当前协议快照最多接受 256 个真实地块，而现有无边画布样本会生成 277 个真实地块；本计划只保证无边模式的渲染与本地战役兼容，不能顺带承诺无边地图联机。若要开放联机，必须另行调整协议上限或同步格式并补回归测试。

## 8. 性能预算

### 8.1 当前原型实测与迁移判断

以下数字来自同一台本地测试机上的浏览器样本，只用于判断当前架构方向，不等同于所有设备上的统一加速倍数：

- 空军压力原型在加入静态战场缓存与防空覆盖缓存后，平均帧耗由约 **87.5 ms** 降至 **18.75 ms**，P95 由约 **116.7 ms** 降至 **33.4 ms**；平均耗时下降约 **79%**。这是缓存和减少重复几何工作的收益，不能记作 PixiJS 自身的加速；
- Pixi 垂直切片压力样本（90 个目标框、60 个防空格、55 个航程格）CPU 提交平均约 **5.77 ms**、P95 约 **8.8 ms**，帧间隔平均约 **16.66 ms**、P95 约 **17.3 ms**；
- 近似 Canvas 矢量样本的 CPU 绘制平均约 **0.525 ms**、P95 约 **1.1 ms**，但帧间隔平均约 **18.27 ms**、P95 约 **54 ms**。该样本与 Pixi 场景不是严格逐像素同构，因此只能说明“Canvas 简单立即绘制的 CPU 成本很低，而 Pixi 在复杂持续动画中帧节奏更稳定”，不能据此宣称 Pixi 有固定倍数优势；
- 当前结论是**值得继续，但只接管高重绘、高长尾、可批处理的 Canvas 管线**：下一优先级为目标框、航程/范围 mask、防空斜纹、动作路线和技能粒子；连续地形、水面/河流、单位、旗帜和战争迷雾暂留 Canvas，分别等缓存收益、遮挡一致性和真实对局 A/B 数据明确后再评审；
- 扩张前先把当前 Pixi 交互层从“逐帧清空并重建 `Graphics`”收敛为保留对象，只更新共享时间、alpha、scale 和少量顶点。若同画质同场景的 P95、输入延迟或内存没有显著优于缓存后的 Canvas，就停止该类迁移。

因此，Pixi 的当前价值不是让所有绘制都更快，而是为大量持续动画、共享状态和批处理覆盖层压低长尾帧；静态或低频图层首先使用 Canvas 缓存往往更便宜。

### 8.2 正式预算

首个 Pixi 生产版本的硬指标：

- 1080p、典型战役地图、40 个单位：中档桌面 GPU P95 帧时 ≤ 16.7 ms；
- 低端或集显设备允许降级到稳定 30 FPS，但输入响应 P95 ≤ 80 ms；
- 静止画面不得因不必要的对象重建持续产生大量 GC；
- 常态 draw calls 目标 ≤ 150，纹理显存预算目标 ≤ 128 MB；
- 地图缩放期间允许临时降低部分粒子与阴影质量，停止缩放后恢复；
- DPR 上限可按设备档位限制为 1、1.5 或 2；
- 静态 chunk 仅在地形、归属、城市 footprint、工事或网格设置变化时重建；
- 单条操作箭头的动态标记上限：移动 ≤ 3、近战攻击 ≤ 4、远程攻击抽象载体 ≤ 1。预览切换只更新该箭头的几何和 uniform，不重建地图 chunk；
- 同一时间只允许一条悬停预览箭头进入逐帧动画，避免大量虚线和粒子占用帧预算；
- 选点模式的合法候选框与中央图案使用批处理几何，并通过同一个低频 `uBreath`/时间 uniform 驱动整体呼吸，不得为每个候选创建独立滤镜或 ticker；同一时间只有 `hoveredTile` 的放大、强辉光、图案增强和范围边界使用独立动态状态；
- 合法候选、上校航程、防空层和范围集合只在选点状态、单位/工事、可见性、天气或棋盘版本变化时重算；呼吸帧只更新共享 uniform/alpha/scale，禁止每帧重新跑候选过滤或 `getAALayers()`；
- 防空单/交叉斜纹使用共享纹理和缓存区域 mask，行军底轨与主轨复用同一条缓存曲线；静态/低频覆盖区优先缓存为纹理，不能每格每帧 `clear()` 后重建复杂 `Graphics`；
- 固定最坏压力样本为“最大支持地图 + 全图合法候选 + 两层防空 + 上校航程 + 范围悬停 + 40 个单位”；连续循环切换六种空军状态，记录 P95 帧时、GC 次数/停顿、纹理显存和 DisplayObject 数量，切换结束后不得持续增长；
- 拆页原型也纳入基线：目录与静态页不得存在 rAF；动态页后台停帧，返回前台后只恢复一条 ticker；页面切换不得保留上一页 Canvas、监听器或高 DPR backing store；
- 性能不达标时先降级阴影、滤镜、粒子和波纹，不降低地形/外交/目标提示的语义可读性。

- 触控设备无需精确 hover：进入现有移动、攻击或卡牌/技能选点态后，单击合法目标仍立即执行；按压/命中反馈只承担静态预览，不新增第二次确认动作。

## 10. 风险与止损线

- **风险：大爆炸式迁移。** 止损：任何阶段都必须保有可运行的 Canvas 后端与特性开关。
- **风险：Pixi 反而增加复杂度。** 止损：规则层禁止依赖 Pixi；若垂直切片无性能收益，停止后续迁移。
- **风险：CanvasSource 每帧上传。** 止损：只允许初始化和脏区重建，开发模式记录上传计数。
- **风险：WebGPU 浏览器差异。** 止损：WebGL 长期作为生产默认，WebGPU 不参与首版交付承诺。
- **风险：2.5D 遮挡牺牲可读性。** 止损：所有装饰必须通过生产尺寸驻军遮挡验收，关键语义永远位于独立 HUD/边界层。
- **风险：水域让规则范围失控。** 止损：首版只实现基础海军、港口和两栖切换；补给、风向、舰队编制另立计划。

## 11. 最终验收定义

只有同时满足以下条件，新的 Pixi 渲染器才可替换默认 Canvas2D：

1. 标准对局、战役模式与六边地图全部通过功能回归；无边地图先按本地/战役渲染能力验收，联机支持必须在协议上限、完整快照、重连与多人压力测试另行通过后才能宣称；
2. 动态阵营、外交色、剧情旗帜、将领挂载、目标高亮和战争迷雾无语义丢失；
3. 视觉金样与已确认原型一致，生产尺寸遮挡下地形仍清楚；
4. 性能达到预算，长时间运行无明显显存/内存增长；
5. WebGL 失败时能自动回退并继续对局；
6. 编辑器可生成、校验、导入和导出新版地形/河流/水域，同时兼容旧 JSON；
7. 至少完成一关陆地战役和一张含河流/海岸的验证关卡试玩；
8. Canvas2D 旧后端的移除必须另行评审，不能随 Pixi 首次上线一起删除。
